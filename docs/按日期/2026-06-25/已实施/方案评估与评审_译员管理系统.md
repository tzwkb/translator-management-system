# 方案评估与评审 — 译员管理系统

> 文档状态：已实施｜日期：2026-06-25｜说明：定制 Web 技术路线已采用。

合并自早先《技术评估》《PRD 评审》两份稿子。源材料是会议转写、`译员管理体系模板.xlsx` 和 `译员管理系统需求文档.md`，怎么落地见 `开发文档_译员管理系统.md`。

## 1. 选型结论

背景：100 多个译员，现在的麻烦是信息散在各种文档和聊天里，价格改了没人记，查不到累计给谁付了多少，档期全靠口头问。

先说不选的：Access。单机、多人易冲突、无法外部登录、敏感数据权限弱、靠 VBA 笨重、难交接，撑不起一个像样的系统。

剩下两条路，低代码（多维表格）和定制 Web：

| | 低代码 | 定制 Web |
|---|---|---|
| 覆盖 | ~85%，CRUD/筛选/看板/提醒/审计/导入导出/权限/深色全内置，1–2 周止血 | 100% 可控 |
| 弱项 | 真加密、PO 硬验算、译员外部门户做不了 | 数周起 + 需长期维护 |

最终选定制 Web（开发文档已按此出）。低代码做不到的几样：支付加密、PO 金额硬核对、译员自助登录，且系统要长期演进。低代码留作备选：先用两周过渡再升级也行，数据模型和规则能直接迁移。

## 2. PRD 评审

PRD（v1.0）写得不错，数据模型基本能直接当规格用。

做对的一点：主表的汇总字段都标了"由各模块自动更新"、不手填。这正是比 Excel 强之处：汇总必须自动算，不靠手敲。

另外找出三个缺口加一个小错，开发文档 §11 都已经修掉：

| # | 缺口 | 严重 | 来源 | 修复（开发文档） |
|---|---|---|---|---|
| 1 | 产能 1:1 快照**丢历史**，而会议最强诉求是「档期变化要留痕」 | 高 | 会议 ↔ PRD §2/§7.2 | §4.4 改时间序列 `capacity_profiles`+`capacity_allocations` |
| 2 | **PO 自动化几乎没写**（会议最看重：日报汇总/25 号批量/开票邮件回收/支付状态） | 高 | 会议 ↔ PRD §11 | §4.8+§5.5 日报→PO→批量开票链路 |
| 3 | 外部译员登录无角色 | 低 | 会议 ↔ PRD §3 | §4.1+§9.4 角色预留、列 V2 |
| 4 | §5.2 字段分组小计标错（标 7/7/7/5，实 5/8/6/7；总数 52 对） | 低 | PRD 自身 | §4.2 修正为 10/10/5/6/8/6/7=52 |

## 3. 开工前要先确认两件事

这两件决定数据怎么存、最难改，须先问清（开发文档 §12 亦列）。一是日报结算数据的来源和格式，决定 PO 如何自动汇总；二是开票做到哪步：半自动（按月汇总成单、人工开票），还是直连发票系统（另立项目）。
