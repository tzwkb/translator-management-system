## 2. 需求背景与问题影响

### 2.1 原始问题

1. 新增 PO 结算行时，译员只能在固定下拉列表中选择，无法按姓名或编号输入联想。
2. 译员的稳定唯一编号（key 值）没有在首页明示，不利于区分同名译员、检索、导出和数据核对。

### 2.2 如不处理可能产生的问题

| 场景 | 风险 |
|---|---|
| 同名译员 | 业务人员只看姓名无法确认真正对象，PO 可能关联到错误记录。 |
| 译员改名/使用别名 | 仅依赖显示姓名时，历史数据与新名称难以稳定关联。 |
| 译员规模增长 | 固定下拉列表越来越长，定位效率下降。 |
| 线下对账 | 导出数据如无稳定 ID，与其他表格合并时只能依赖姓名。 |
| 用户手动修改姓名 | 如果页面仍保留上一个译员 ID，显示文本与实际提交对象可能不一致。 |

## 5. PO 译员组合框设计

### 5.1 显示值与提交值分离

| 元素/数据 | 用途 | 业务含义 |
|---|---|---|
| `p-translator_name` | 用户可见的姓名/ID 输入框 | 用于搜索和显示，不直接作为数据关联依据 |
| `p-translator_id` | 隐藏域 | 仅保存已确认的稳定译员主键 |
| `p-translator-menu` | 联想结果容器 | 展示可选译员，为同名场景提供 ID 辨识 |
| `PO_TRANSLATORS` | PO 页译员数据源 | 优先使用与 PO 页同步的候选集合 |
| `DATA` | 回退数据源 | PO 候选集未加载时，使用首页已加载数据 |

这个设计的核心约束是：姓名可以改变，主键不能通过自由文本伪造。

### 5.2 组合框状态转换

| 状态 | 姓名框 | 隐藏 ID | 菜单 | 允许保存 |
|---|---|---|---|---|
| 初始/新增 | 空 | 空 | 关闭 | 否 |
| 获取焦点 | 当前文本 | 保持当前状态 | 展开匹配结果 | 取决于 ID 是否有效 |
| 手动输入 | 更新 | 立即清空 | 按新文本重新联想 | 否 |
| 选中结果 | 写入标准姓名 | 写入选中 ID | 关闭 | 是 |
| 精确输入唯一命中 | 写入标准姓名 | 写入命中 ID | 关闭 | 是 |
| 无匹配 | 保留用户文本 | 空 | 显示“无匹配译员” | 否 |
| 编辑回填 | 按 ID 恢复标准姓名 | 原 PO 的 ID | 关闭 | 是 |

### 5.3 匹配规则

`translatorMatches()` 对用户输入做去首尾空格和小写归一化，然后执行包含匹配。

| 输入示例 | 匹配逻辑 | 结果 |
|---|---|---|
| 空字符串 | 不限定查询 | 展示当前可用译员列表 |
| `王` | 姓名中包含该文本 | 返回所有命中姓名 |
| `12` | 将 ID 转为字符串后执行包含匹配 | 返回 ID 中包含 `12` 的译员 |
| 完整 ID | ID 精确匹配 | 如只有一条记录，可直接确认 |
| 完整姓名 | 归一化后精确匹配 | 仅命中一条时自动确认 |
| 重复姓名 | 精确匹配到多条 | 不自动提交，需要用户通过 ID 明确选择 |

### 5.4 联想结果渲染

- 每个结果使用独立按钮，点击后传入数字 ID。
- 主文本显示译员姓名，辅助文本显示“唯一编号 + ID”。
- 译员姓名通过页面现有 `esc()` 逻辑输出，避免名称被当作 HTML 插入。
- 无结果时保留菜单容器，显示明确空状态，不让用户误以为页面失效。

### 5.5 键盘、焦点与菜单定位

| 交互 | 处理 |
|---|---|
| 输入框获取焦点 | 展开当前匹配结果 |
| 点击展开按钮 | 在展开/关闭之间切换，展开时将焦点返回输入框 |
| `ArrowDown` | 阻止默认行为并展开联想菜单 |
| `Enter` | 菜单展开时选择当前首个匹配项 |
| `Escape` | 关闭联想菜单 |
| 点击组合框外部 | 关闭联想菜单 |
| 弹窗/页面滚动 | 根据输入框当前坐标重算菜单位置 |
| 窗口尺寸改变 | 重算菜单位置，避免尺寸变化后偏移 |

组合框已配置 `role="combobox"`、`aria-autocomplete="list"`、`aria-controls` 和动态 `aria-expanded`，为后续完善无障碍键盘导航保留标准结构。

## 6. PO 业务链路保持与增强

### 6.1 新增 PO 流程

1. `openPO()` 调用 `setPOTranslator(null)`，同时清空姓名和隐藏 ID。
2. 清空上一次的项目、数量、单价、金额、PO 号和备注。
3. 根据当前 PO 筛选状态确定默认结算月。
4. 将计价模式恢复为按千字，角色恢复为翻译。
5. 打开 PO 弹窗，等待用户选择译员。

### 6.2 选中译员与自动取价

1. `pickTranslator(id)` 调用 `setPOTranslator(id)`。
2. 系统从候选译员中按数字 ID 查找标准记录。
3. 页面同步写入标准姓名和隐藏 ID，并在输入框 `title` 中保留唯一编号。
4. 关闭联想菜单，将焦点返回输入框。
5. 调用 `fillPORate()`，使用译员 ID、项目、语言对、角色和币种查询现有价格规则。
6. 匹配成功后更新计价模式、单价、金额、币种和提示文案。

### 6.3 编辑 PO 流程

1. `editPO(id)` 从已加载 `PO_ROWS` 中找到原 PO。
2. 使用原 PO 的 `translator_id` 调用 `setPOTranslator()`，而不是根据姓名反查。
3. 回填结算月、项目、语言对、角色、计价模式、数量、单价、金额、币种、状态、PO 号和备注。
4. 调用 `updatePOPricing()` 恢复字段启用状态和计价提示。
5. 保存时继续根据 PO ID 走现有 PUT 更新链路。

### 6.4 保存前数据保护

`savePO()` 不直接信任姓名输入框，而是从隐藏域读取并数字化 `translator_id`。以下任一情况均不能作为有效译员提交：

- 译员框为空。
- 只输入部分姓名，但未选中联想项。
- 选中后又手动改动姓名文本。
- 输入不存在的 ID。

上述情况会在前端提示“请从联想结果中选择译员”，不进入 PO POST/PUT 提交。

## 7. 首页唯一编号数据闭环

唯一编号不再只存在于后端数据中，而是进入用户日常查询、核对和导出流程。

`row.id` → 首页表格 → 全局搜索 → Excel 式列筛选 → 筛选结果导出 → 译员详情摘要。

| 功能面 | 实现内容 | 核对意义 |
|---|---|---|
| 表格列 | 新增“唯一编号”表头与 `t.id` 数据单元格 | 用户不打开详情即可确认主键 |
| 顶部搜索 | 搜索文本同时与 `String(row.id)` 匹配 | 获得 ID 后可直接定位译员 |
| Excel 式筛选 | 在 `EXCEL_COLUMNS.tr` 中将 `id` 注册为数字字段 | 可使用数字等于、区间等现有筛选能力 |
| 导出 | 筛选结果 CSV 列集合新增 `id` | 线下表格可按主键合并和去重 |
| 详情摘要 | 新增“唯一编号”摘要标签 | 详情与首页数据可交叉确认 |
| 搜索提示 | 输入框占位文案补充“编号” | 显式告知用户新的查询能力 |

## 8. 关键函数与职责划分

| 函数 | 职责 | 关键约束 |
|---|---|---|
| `poTranslators()` | 返回 PO 译员候选数据 | 优先 `PO_TRANSLATORS`，必要时回退 `DATA` |
| `translatorMatches(query)` | 按姓名或 ID 过滤候选译员 | 姓名做小写归一化，ID 转字符串匹配 |
| `positionTranslatorMenu()` | 计算联想菜单坐标和宽度 | 只在组合框展开时执行 |
| `openTranslatorMenu()` | 生成联想结果并打开菜单 | 展开译员菜单前关闭语言菜单 |
| `toggleTranslatorMenu()` | 处理展开按钮 | 同步焦点与展开状态 |
| `translatorInputChanged()` | 处理用户自由输入 | 先清空旧 ID，再重新匹配 |
| `commitTranslatorInput()` | 处理精确姓名/ID 确认 | 只有唯一精确命中才选中 |
| `setPOTranslator(id)` | 按 ID 统一设置姓名和隐藏主键 | 查不到记录时同时清空两个字段 |
| `pickTranslator(id)` | 完成用户选中动作 | 设置译员后触发现有取价逻辑 |
| `closeTranslatorMenu()` | 关闭菜单 | 同步更新 `aria-expanded=false` |
| `translatorKeydown(event)` | 处理基本键盘交互 | 支持展开、选择首项和关闭 |
| `openPO()` | 初始化新增 PO | 必须清空旧译员主键 |
| `editPO(id)` | 回填已有 PO | 必须使用 `translator_id` 恢复译员 |
| `fillPORate()` | 查询并回填匹配价格 | 从隐藏主键读取译员 ID |
| `savePO()` | 组装并提交 PO | 无有效 `translator_id` 时不发起接口请求 |

## 9. 数据完整性与异常处理

| 场景 | 处理方式 | 目的 |
|---|---|---|
| 候选数据尚未加载 | 从 `PO_TRANSLATORS` 回退到 `DATA` | 减少页面加载时序对组合框的影响 |
| 查询无匹配 | 显示“无匹配译员” | 为用户提供明确反馈 |
| 姓名文本被改动 | 清空隐藏 ID 和编号提示 | 防止提交过期主键 |
| ID 查不到译员 | `setPOTranslator()` 将姓名和 ID 都置空 | 避免展示不存在的关联 |
| 未选中译员便保存 | 前端阻断并显示错误提示 | 防止无效外键进入业务链路 |
| 未选译员便触发取价 | `fillPORate()` 在 ID 为空时直接返回 | 避免发起无意义的价格请求 |
| 联想项姓名含特殊字符 | 使用 `esc()` 输出 | 保持页面结构完整 |
| 菜单与语言菜单同时打开 | 打开译员菜单时关闭语言菜单 | 减少弹层重叠和操作歧义 |

## 10. 接口、数据库与兼容性

### 10.1 后端契约

- 没有新增或修改后端 API。
- 没有数据库迁移，也没有修改译员或 PO 表结构。
- PO 新增仍走现有 POST 链路，编辑仍走现有 PUT 链路。
- 提交字段仍为 `translator_id`，未改为姓名或其他不稳定标识。
- 价格查询仍调用现有 `/api/po/price-match`。

### 10.2 可见行为变化

- 首页表格新增一列，表格总宽度会随之增加。
- 首页 CSV 导出新增 `id` 列，且放在姓名之前。依赖旧列序的线下模板应按列名读取，不应只按列位置读取。
- PO 译员字段变为可输入组合框，但最终数据契约保持不变。
- 顶部搜索框占位文案补充“编号”，用于暴露新能力。
