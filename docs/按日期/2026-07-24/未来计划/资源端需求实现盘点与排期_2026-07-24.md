## 三、关键设计结论

### 1. 当前项目和过往项目应使用同一张明细表

不要继续给译员主表加“当前项目 2/3”和“过往项目”长文本。建议一行代表一次项目经历：

```text
translator_id
cooperation_source = our_company / external
project_status = current / past
project_name
client_or_company
role
source_locale / target_locale
start_date / end_date
remaining_volume / deadline / occupancy_pct
remarks
```

“当前/过往”是状态，“我司/别家”是来源，二者是两个独立维度。这样第 1、2、6、7、8 项才能共用同一数据源。

### 2. “一口价”是计价方式，“其他”是自定义任务类型

建议不要简单再给 `language_pairs` 表加两列：

- 一口价：`pricing_mode = fixed`，必须关联项目/任务，并直接保存固定总价。
- 常规价格：`pricing_mode = per_unit`，单位可为千字、小时、条等。
- 其他：`task_type = custom`，同时要求 `custom_task_name`，例如“角色命名审核”“活动文案润色”。

PO 金额规则相应变为：

```text
fixed      -> amount = quoted_amount
per_unit   -> amount = quantity × unit_rate
per_1000   -> amount = quantity / 1000 × unit_rate
```

### 3. 档期应采用“人工确认 + 系统计算”双轨

只靠手动会过时，只靠计算又会因项目量不完整而误判。建议同时展示：

- `declared_availability`：译员/资源端最近确认的档期，带确认日期和有效期。
- `computed_availability`：系统按剩余量、截止日期、日产量和占用率计算。
- `availability_conflict`：两者不一致时提醒复核，不静默覆盖人工信息。

计算建议：

```text
可用率 = 100 - 当前窗口内各项目负荷%
空闲 = 可用率 >= 80%
部分空闲 = 50% <= 可用率 < 80%
满负荷 = 可用率 < 50%
```

若项目没有剩余量/截止日期，则系统只能使用现有人工录入的 `occupancy_pct`，并把结果标成“估算”。

### 4. 第 9 项不是简单增加几个表头别名

实际工作簿中：

- `项目组日报表2.0` 的表头在第 2 行，字段是 Owner、归属项目+批次、任务类型、投入工时等；它没有完整的译员、费率、币种和结算月，不能单独生成译员 PO。
- 真正的译员结算数据在 `【项目组】Projectlist (V1.0)`，表头在第 3 行，包含“指定译员、工作类型、翻译费率、币种、译员 WWC 字数、REPNEW 实际、译员 PO 时间、结算 PO、原语言、目标语言”等。
- 当前导入器读取活动工作表并固定使用第 1 行表头，因此导入该原始文件会得到 0 行或无法映射。

正确流程应为：

```text
原始工作簿
  -> 自动识别 Projectlist 和表头
  -> 按固定字段映射生成导入预览
  -> 人工只处理未匹配或金额异常行
  -> 批量确认入账
```

以后每月直接导入原始文件，不需要先人工改成系统模板。首版用文件哈希防止整份文件重复导入；若后续出现同一文件反复修订，再增加行级指纹和持久化别名映射。

### 5. 累计结算不应改写历史月份

每月工作量仍应按发生月保存。新增“付款批次”把多个月份的未付明细归到一次支付中：

```text
1 月工作明细 ┐
2 月工作明细 ├─> 3 月累计付款批次 -> 已支付
3 月工作明细 ┘
```

这样既能看到每月发生额，也能看到累计到哪一次付款，不会把前几个月数据挪到结算月。

### 6. 支付方式应拆成多账户，而不是继续扩一张银行表

建议每个译员/供应商可维护多个账户并指定默认账户：

| 方式 | 主要字段 |
|---|---|
| 微信 | 实名、微信号/手机号、收款码附件（如业务需要） |
| 支付宝 | 实名、支付宝账号/手机号 |
| 个人银行卡 | 收款人、银行、支行、卡号、证件信息 |
| 对公人民币 | 公司/账户名、开户行、账号、税号 |
| 对公美金 | Beneficiary、账号/IBAN、银行名与地址、SWIFT/BIC、Routing/ABA、Intermediary Bank |

精确必填字段要由财务在开发前确认。所有账号和证件类字段继续加密、默认脱敏，查看明文必须记审计。

### 7. 语言代码与显示名分离

存储采用规范化 BCP 47 标签；中英文名称从 CLDR 生成。示例：

```text
存储：zh-Hans -> en-US
简中显示：简体中文（zh-Hans）→ 英语（美国）（en-US）
英文显示：Simplified Chinese (zh-Hans) → English (United States) (en-US)
```

参考：

- RFC 5646 / BCP 47: https://www.rfc-editor.org/info/rfc5646/
- Unicode CLDR locale display names: https://cldr-smoke.unicode.org/spec/main/ldml/tr35-general.html

## 五、开发前必须确认的业务口径

1. **过往项目**：别家公司名称是否必填；是否需要保密/模糊展示。
2. **一口价**：金额是整项目、某批次还是某任务；能否跨语言对复用。
3. **其他价格**：需要自由输入名称，还是维护受控价格类型字典。
4. **档期**：人工确认有效期；剩余量、DDL、工作日和双休如何参与计算。
5. **每语种人数**：按母语统计、目标语言统计，还是两张图都要。
6. **价格筛选**：示例中的 150–300 是哪种任务、哪种单位、哪种币种；不同币种不应直接混筛。
7. **Projectlist 数量列**：翻译、LQA、小时任务分别取哪一列；REP/WWC 折算规则。
8. **累计结算**：按时间、金额门槛，还是资源端手动触发；跨币种是否必须分批。
9. **支付字段**：微信/支付宝是否收二维码；对公美元是否要求中转行、ABA/IBAN、银行地址。
10. **资质文件**：允许的格式和单文件大小；谁能查看、下载、删除。
