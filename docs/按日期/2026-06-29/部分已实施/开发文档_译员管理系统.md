## 1. 范围

这份覆盖技术栈、目录、数据库 DDL、业务逻辑、API、权限与安全、前端、部署、时间节点。枚举值不重抄，直接看 PRD §15。

数据量不大（100 多个译员，各表千行级，最多 20 人同时用），不上 Redis、Celery、微服务。提醒用进程内 APScheduler，缓存用数据库的物化视图和快照表即可。量上来再加，§9.4 标了在哪加。

## 2. 技术栈（确定版）

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Python 3.12 + FastAPI + SQLAlchemy 2.0 + Alembic** | 贴合现有 Python 工具链；Alembic 管迁移 |
| 数据库 | **SQLite（开发）→ PostgreSQL（上线）** | 零配置起步，迁移只需换连接串（与部门看板一致） |
| 鉴权 | **JWT（access 30min + refresh）**, bcrypt | PRD §14.2 |
| 定时任务 | **APScheduler（进程内）** | 此规模不需 Celery+Redis |
| 加密 | **cryptography（AES-256-GCM 字段级）** | PRD §9/§14.2 |
| 前端 | **纯 HTML/CSS/JS + ECharts（单文件，无框架）** | 与部门看板同款；零依赖，引后端 API 即可 |
| 导入导出 | **openpyxl / pandas** | xlsx/csv |
| 部署 | **本地启动脚本 + FastAPI 挂静态文件**（同部门看板） | uvicorn 起服务、浏览器开页面即用 |
| 缓存(可选) | Redis | 仅当仪表板/并发压力出现再加 |

和「部门看板」用同一套栈、同一套底座。登录、RBAC、通用增删改查、单文件 HTML 前端壳、Alembic 迁移、openpyxl 导出全部复用，users 和 departments 共享一套，译员系统就是同一个后端项目里多加的一组表和页面。

两边怎么接：译员的明细数据存在译员系统这边，部门看板资源组要的「译员 TOP5、成本、招聘」直接从这里汇总取，不另存一份。

### 4.4 产能排期（时间序列，修缺口1）

（修缺口1）PRD 原来的设计是每个译员一条记录、W1–W5 几个列，新数据一来就把旧的盖掉，留不住历史，可会议上最强调的就是档期变了要有记录。改成两张表：一张 1:1 的产能基线，一张按月、按周往里追加占用行，历史自然就留下来了，看当前情况取最新一个月。

### 4.8 PO 结算 + 自动化链路（修缺口2）

（修缺口2）会议上 PO 这块讲得最多：不能自动化、日报结算不够智能、25 号要批量发 PO、开票要邮件回收、还要看支付状态。这里补一条链路：日报先进一张源表，自动汇总成 PO，再按批次批量开票、发邮件、跟状态。


## 5. 核心业务逻辑与算法

### 5.1 主表汇总字段同步（最要紧的一条）
`translators` 里标了 `[derived]` 的字段不靠人填，是子表一增删改就在同一个事务里调 `RecalcService` 重算出来的：

| 子表写入 | 重算 translators 字段 |
|---|---|
| quality_scores | recent_qa_score=最新score；cumulative_qa_score=AVG(score)；low_error_count=Σminor；low_error_rate=Σminor/Σword_count×1000 |
| rate_changes(result='成功') | translation/对应费率←new_rate；last_negotiation_date；post_negotiation_rate；rate_reduction_pct；negotiation_status |
| contracts | contract_status/contract_expiry=最新有效合同；nda_signed |
| complaints | complaint_count+1；deduction_total+=deduction_amount |
| po_settlements/daily_reports | cumulative_unpaid=Σ(待付)；cumulative_word_count |
| capacity_allocations | availability=最新月可用率档位 |

放在 service 层、不用数据库触发器，便于测试和审计。每天跑一次 `reconcile_job` 全量重算纠偏。

### 5.2 质量评分（可配置）
公式存 `system_configs['qa_formula']`，默认（PRD §6.3.1）：
```
total = accuracy×0.30+fluency×0.25+terminology×0.20+style×0.10+formatting×0.10+localization×0.05
        - (critical×15 + major×5 + minor×1)
rating: S≥95 / A85-94 / B75-84 / C60-74 / D<60   (PRD §15)
```

### 5.3 PO 金额核对（硬规则，PRD §11/§13.5）
每次写入或更新都校验 `|amount - wc×rate| ≤ 0.02`，对不上就拒绝、标红。汇总页也强制核对：`待付 = Σ已开票待付 + Σ未开票`、`已付 = Σ已支付`，分项加起来跟合计对不上就告警，每个合计都标清楚是怎么算的。

### 5.4 产能计算
可用率、占用、冲突、空闲档位都按 PRD：某周可用率 = 100 − 该周各项目占用之和（PRD §5.2 字段定义），占用之和超 100% 即超负荷标红（PRD §7.3.2）；档位按 PRD §15 的 ≥80 空闲 / 50–80 部分空闲 / <50 满负荷。

产能利用率字段已删（0629 资源方决定：算着复杂、参考意义不大，档期直接问译员本人）。

甘特看板默认显示最新月，可切历史月（缺口1）。

### 5.5 PO 自动化（缺口2 落地）
分四步。先自动汇总，`po_generate(settlement_month)` 把 `daily_reports` 按译员、月、项目、角色聚合成 `po_settlements`（金额求和，回填 `daily_reports.po_id`），归到一个 `po_batches` 批次里。然后是 25 号批量，APScheduler 每月 25 号建好当月草稿批次，资源或财务复核完一键 `issue`，状态转成已开票待付，可以批量导出 PO、触发邮件。开票回收靠记 `invoice_sent_at / invoice_received_at / invoice_email_msgid` 这几个时间点，用状态机跟。支付状态按 未开票、已开票待付、已支付 往下走，有争议单挂一档；每次变更都记时间、记是谁改的、进审计。

真要对接金税或电子发票是以后的事，这期只做到半自动加状态全程可见。

### 5.6 提醒调度（APScheduler, 每日 09:00）
扫描并写 `notifications`（+可选邮件）：合同 30/14/7/1 天到期、NDA 30/7 天、已过期未处理、本周释放档期、未来 7 天休假、PO 状态变更、新客诉。阈值读 `system_configs`。

### 5.7 加密与脱敏（PRD §9）
`bank_account`、`tax_id`、`id_card` 这三个用 AES-256-GCM 加密，密钥放环境变量或 KMS，不进库也不进仓库。平时返回默认脱敏，显示成 `**** **** 1234`、`320***…1234` 这样。要看完整内容得二次确认，解密后还要写一条审计。导出明文要单独授权。

## 7. 权限（RBAC + 行级 + 列级）

角色矩阵按 PRD §3 那张表，中间件按 角色×模块×动作 放行。行级上，PM 查数据时自动加一句 `project_id IN (SELECT project_id FROM project_members WHERE user_id=?)`，只看得到自己项目。列级按角色裁字段：财务看得到费率但改不了，QA 能改质量字段但碰不了合同，做法是 Pydantic 响应模型按角色选、写接口加字段白名单。所有增删改都进 `audit_logs`，记下改前改后。

## 13. Agent 接口与服务账号（部分已实现）

demo 已落地核心护栏；自然语言那层按计划由外部 skill 承担。

### 13.1 已实现（demo）
- agent 用**独立服务账号**（token 角色 agent）。
- agent 写：档期等低风险**直接落**；**费率、PO 进 `pending_changes` 待审队列，editor 批准才生效、驳回作废**——会上「涉及钱必须人工核验」由权限层强制。
- 费率/PO 写逻辑抽成 service 函数，「直接写」与「批准后写」共用一套。
- 审计记到 agent 名下，人与 agent 分得清。

### 13.2 还差
- service 层只覆盖 rate/PO，其余模块逻辑仍在接口函数里。
- 没有 `/api/agent` 自然语言入口——按计划由外部 skill（Claude）做 NL→工具调用，调系统 REST 工具 + agent token。
- 没有 dry-run、幂等。

### 13.3 服务账号与 token（上服务器后）
- agent 用**独立服务账号**，不借人的 token。
- 原因：审计能分清人与 agent（系统已有审计日志）；最小权限（只给低风险写，钱相关只能提建议）；可单独吊销/轮换，泄露不波及任何人。
- production 权限要比现在 editor/viewer 细——按模块、字段、动作（如「可写产能，费率只能提交建议」），agent 账号挂最严一档。
- 两种用法：后台自动化（如微信/企微定时抓取）用 agent 独立身份；人当面用自然语言指挥，走「代表某人」的临时 token，日志仍标「经 agent」。

### 13.4 典型自动化（示例）
微信/企微定时抓取 → LLM 抽取译员信息（档期/联系/新译员）→ 写系统：低风险自动落库，费率等进待审队列。production 形态是后端定时任务 + LLM，不是常驻聊天循环。
