# 译员语言对 数据结构方案（评审稿）

> 文档状态：已实施（后续有迭代）｜日期：2026-06-29｜说明：独立语言对子表已落地；费率已进一步扩展为每语言对独立费率。

## 1. 背景与目标

当前 `translation_rate` 等在译员主表，`language_pairs` 存成单字段组合串（`ZH→EN,ZH→JA`）。三个现实约束推动重新选型：

- 一个译员常有**多对**语言（PRD §5.2 原本就是多值 `["ZH→EN","ZH→JA"]`）。
- 语言对是**核心筛选 / 统计维度**：仪表板「语言对覆盖」、招募按语言对筛、「谁能做 →EN」。
- 不同语言对**费率可能不同**（ZH→EN 与 ZH→JA 不一定同价）。

目标：选一个既装得下多对、又好筛好统计、还不让资源端难填的结构。

## 2. 候选方案

### A. 组合字符串（现状）

主表一个字段 `language_pairs = "ZH→EN,ZH→JA"`。

- 优：最简单，零改动，Excel 一个格。
- 缺：筛选靠子串 `LIKE '%→EN%'`（不利落、易误伤，如把 `→ENG` 也命中）；装不下「每对费率」；不规范。

### B. 主表两个多值列

`source_langs = "ZH,ZH"` + `target_langs = "EN,JA"`。

- 优：源/目标能分开筛。
- 缺：多对时**对应关系糊**——`源=ZH,JA / 目标=EN,KO` 谁配谁分不清；本质比 A 更差。**不推荐**。

### C. 语言对子表（独立表，一行一对）★

```python
class LanguagePair(Base):
    __tablename__ = "language_pairs"
    id: Mapped[int] = mapped_column(primary_key=True)
    translator_id: Mapped[int] = mapped_column(ForeignKey("translators.id"), index=True)
    source_lang: Mapped[str] = mapped_column(String(20))   # ZH / EN / JA …
    target_lang: Mapped[str] = mapped_column(String(20))
    rate: Mapped[Optional[float]] = mapped_column(Numeric(10, 2))   # 可选：该对单独费率
```

数据示例（张明两对 = 两行）：

| id | translator_id | source_lang | target_lang | rate |
|----|---------------|-------------|-------------|------|
| 1 | 1（张明） | ZH | EN | 180 |
| 2 | 1（张明） | ZH | JA | 200 |
| 3 | 2（李娜） | ZH | JA | 220 |

- 优：规范（第一范式）；按源 / 目标 / 整对任意筛，列可加索引；天然容纳每对费率；与系统现有 6 张子表（报价 / 质量 / 合同 / 客诉 / 产能 / 支付）同一种 1 对多模式；与 agent 现有 src/tgt 模型对齐。
- 缺：多一张表；查译员列表要 join / 聚合；前端加一个语言对子表录入。

### D. JSON 字段

主表 `language_pairs JSON = [{"src":"ZH","tgt":"EN","rate":180}, ...]`。

- 优：一个字段装多对 + 每对属性；不加表；贴 PRD 字面「JSON/多值」；整体一次读写。
- 缺：筛选靠 DB 的 JSON 查询（SQLite/PG 都支持但写起来绕、索引弱）；跨对统计要在应用层展开；不如子表利落。

## 3. 横向对比

| 维度 | A 组合串 | B 多值列 | **C 子表** | D JSON |
|------|---------|---------|-----------|--------|
| 装多对语言 | ✓ | ✓ | ✓ | ✓ |
| 按源 / 目标筛 | 子串·易误伤 | 半·对应糊 | **✓ 索引** | 弱·JSON查询 |
| 每对独立费率 | ✗ | ✗ | **✓** | ✓ |
| 跨对统计（语言对覆盖） | 难 | 难 | **✓** | 需展开 |
| 规范化 | ✗ | ✗ | **✓** | 半 |
| 加表 / 改动成本 | 0 | 低 | 中 | 低 |
| Excel 影响 | 无 | 无 | 导入拆行·**模板不变** | 导入转JSON·模板不变 |
| 查译员列表 | 直接 | 直接 | 需 join/聚合 | 直接 |
| 与现有 6 子表一致 | — | ✗ | **✓** | ✗ |
| 与 agent src/tgt 对齐 | ✗ | 半 | **✓** | 半 |

## 4. 推荐：C 语言对子表

四条理由：

1. **语言对是主查询维度。** 仪表板覆盖统计、招募筛选都按它走；索引化的关系列在筛选与聚合上完胜 JSON 与子串。
2. **天然容纳每对费率。** 费率按语言对不同时，直接落在子表的 `rate`，不必为此另设结构。
3. **架构一致。** 系统已有 6 张 1 对多子表，再加一张语言对子表是同一套模式，前后端都有现成范式可抄，维护成本低。
4. **对齐 agent。** agent 现有 `tables.py` 就是源/目标分开，子表与之天然吻合，统一模板时少做转换。

D（JSON）是次选——更省事、贴 PRD 字面，但语言对作为核心筛选维度，JSON 的查询弱点是硬伤。A 仅适合「先跑起来」的 demo 阶段（即现状）。B 不取。

## 5. 数据库架构统一性（配套决策）

语言对怎么存，牵动整库几条统一规则。逐条定，确认整体一致再动手——不只为语言对，是为整库口径一致。

### 5.1 费率的归属——语言对 vs 任务类型（最关键）

现状：主表有 `translation_rate / mtpe_rate / review_rate / lqa_rate`（按**任务类型**、每译员一套）；`rate_changes` 子表记调价历史（带 `task_type`）；`resync` 把「翻译·成功」的调价同步回主表。

问题：语言对子表要不要也带费率？带了就和上面三处费率重叠，口径会乱。

| 选项 | 说明 | 评 |
|------|------|----|
| a 正交★ | 语言对子表只管「能做哪些对」、**不带费率**；费率维持「按任务类型 → 主表 + rate_changes 记历史」 | 语言对=能力，费率=任务类型，两维度不掺，口径单一 |
| b 每对每类型一价 | 费率全挪进语言对子表（`src,tgt,task_type,rate`） | 最细，但和 rate_changes 职责重叠、复杂 |
| c 覆盖价 | 主表留默认价，语言对子表加可空 `rate` 作「该对覆盖价」，空则用默认 | 折中，业务确认每对不同价时再启用 |

**推荐 a 正交**——这是统一性的关键：费率只有一个归属（任务类型 × 主表/历史），不被语言对拆散。除非 Raven/PM 明确「同译员同任务类型、不同语言对价格不同」，否则费率不进语言对子表；真要拆再走 c 覆盖价，不破坏正交。
→ 据此 §2 的 C 方案**去掉子表 `rate` 列**（仅走 c 时才加）。

### 5.2 多值字段拆不拆——统一判定标准

多值字段不止语言对，还有 `domains 擅长领域 / text_types 文本类型 / cat_tools CAT工具`（现存逗号串）。定一条统一规则，别逐个拍。

**判定（满足任一就拆子表，否则留串/JSON）**：
1. 是**核心筛选/统计维度**（要按它 join、聚合、出报表）；
2. 每个值要带**自己的属性**（如每对费率）；
3. 需要**引用完整性**（受控词表、防乱填）。

按此：
- `language_pairs` → **拆子表**（命中①，可能②）。
- `domains / text_types / cat_tools` → **留逗号串**（标签性质，筛选需求弱、无附加属性）；日后要按领域出报表，再按同一规则升级。

→ 当前只 language_pairs 够格拆，其余维持；标准统一、可复用。

### 5.3 子表统一骨架

语言对子表与现有 6 张子表**同骨架**，不各搞各的：

- `id` 自增主键；
- `translator_id` 外键 + 索引（各子表已有惯例）；
- 上线/PG 版统一加 `created_at`（`updated_at` 按需）；
- **删除策略统一**：主表软删（`deleted_at`），**子表不单独软删**——主表软删时子表行随之保留（主表未真删）。

→ 所有子表（含语言对）走这一套。

### 5.4 主表缓存字段的一致性

选 C 后，主表 `language_pairs` 串建议**留作只读展示缓存**（列表页一眼看语言对，不必每行 join）。它和已有派生字段（`recent_qa_score`、`complaint_count`、被调价同步的 `translation_rate`）性质相同——都是**由 service 从子表/子记录重算、不手填**。

**统一规则**：主表凡「由子表汇总来的」字段，一律纳入现有 `resync_translator` 那套重算机制，单一出处维护。语言对显示串、（若走覆盖价的）主表默认费率，都按此。

### 5.5 主表宽窄取向（总纲）

把上面收成一条总取向，确认整库一致：

> **标量属性**（姓名、状态、各任务类型费率…）→ **主表**
> **多值 / 历史 / 关系**（语言对、调价、合同、PO、客诉、产能…）→ **子表**
> **跨子表汇总**（QA 分、客诉数、语言对显示串…）→ 主表的**只读缓存**，由 service 重算

语言对拆子表是这条取向的**延续，不是新范式**——和现有 6 子表 + 派生缓存完全一致。

### 5.6 落地改动（选 C 后）

- 后端：新增 `language_pairs` 表 + 语言对增删查接口；译员 `as_dict` 把语言对收成数组返回。
- 导入：「语言对」格 `ZH→EN,ZH→JA` 拆成多行写子表（**Excel 模板不变**）。
- 前端：详情页加「语言对」子表录入；列表「语言对」列由缓存串展示。
- 迁移：现有主表 `language_pairs` 串按逗号拆成子表行 + 回填缓存串。
